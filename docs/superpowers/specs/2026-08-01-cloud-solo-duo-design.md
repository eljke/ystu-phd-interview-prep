# Облачная соло- и парная подготовка

## Цель

Приложение должно поддерживать подготовку одного человека и пары на двух устройствах. Вход выполняется только через GitHub OAuth. Успешная OAuth-аутентификация не даёт доступ автоматически: пользоваться приложением могут только GitHub-аккаунты из активного whitelist.

Учебный контент и статические файлы остаются публичными на GitHub Pages. Персональные данные, прогресс, сессии и аудиозаписи доступны только авторизованным и допущенным пользователям.

## Принятые решения

- Сохранить React, Vite, HashRouter, PWA и GitHub Pages.
- Использовать Supabase Auth, Postgres, Realtime и private Storage.
- Сохранить Dexie как локальный кеш и очередь офлайн-изменений.
- Считать Postgres источником истины для облачных данных и состояния парных сессий.
- Разделить GitHub-пользователя, учебный профиль и пару.
- Не добавлять встроенный аудио- или видеозвонок.
- Не добавлять распознавание речи и автоматическую оценку ответа на первом этапе.
- Запись голоса локальна по умолчанию; загрузка партнёру выполняется только явно.

## Контроль доступа

### Аутентификация

Supabase Auth использует GitHub OAuth. Клиент содержит только Supabase URL и publishable key. GitHub OAuth secret и Supabase service role key никогда не попадают в Vite-конфигурацию или браузер.

После OAuth callback приложение выполняет серверную проверку допуска. Пользователь получает рабочую сессию приложения только при выполнении всех условий:

1. OAuth provider — GitHub.
2. GitHub-аккаунт сопоставлен с постоянным числовым GitHub user ID.
3. Для этого ID существует активная запись whitelist.
4. Запись не отозвана администратором.

Если проверка не пройдена, приложение очищает локальную auth-сессию и показывает страницу «Доступ не предоставлен». Пользователь не может читать или изменять прикладные таблицы даже при ручных запросах к Supabase API.

### Whitelist

Администратор вводит GitHub login. Защищённая Edge Function получает пользователя через GitHub API, сохраняет одновременно:

- нормализованный текущий login;
- постоянный числовой GitHub user ID;
- роль `member` или `admin`;
- состояние `active` или `revoked`;
- автора и время изменения.

Числовой ID является ключом допуска. Login служит для поиска и отображения, поэтому переименование GitHub-аккаунта не передаёт доступ новому владельцу старого login.

Первый администратор добавляется одноразово через Supabase Dashboard/SQL после применения миграций. В репозиторий не записываются секреты.

### Авторизация данных

RLS включается для всех прикладных таблиц и Storage. Базовое условие каждой политики — текущий `auth.uid()` принадлежит активному допущенному пользователю.

Дополнительно:

- личные данные доступны только владельцу;
- данные пары доступны только двум активным участникам пары;
- административные таблицы и операции доступны только роли `admin`;
- аудиофайл доступен автору и назначенному партнёру;
- service role используется только внутри защищённых Edge Functions.

Проверка допуска в интерфейсе нужна для UX, но не заменяет RLS.

## Доменная модель

Основные сущности:

- `access_entries` — whitelist и роли;
- `app_users` — связь Supabase user с GitHub identity и учебным профилем;
- `pairs` — активная или архивная пара;
- `pair_members` — ровно один или два участника;
- `pair_invites` — одноразовые приглашения с ограниченным сроком;
- `topic_progress` — личный прогресс пользователя по теме;
- `quiz_attempts` — неизменяемые попытки тестов;
- `oral_attempts` — самостоятельные и парные устные попытки;
- `partner_assessments` — оценка ответа партнёром;
- `study_sessions` — соло- и парные занятия;
- `live_pair_sessions` — сохраняемое состояние синхронной сессии;
- `audio_recordings` — метаданные приватных объектов Storage;
- `admin_audit_log` — изменения whitelist.

Один пользователь может готовиться без пары. В первой версии у пользователя может быть не более одной активной пары, а в активной паре — не более двух участников. Эти ограничения обеспечиваются БД, а не только интерфейсом.

## Репозитории и синхронизация

Существующий `StudyRepository` не должен превращаться в универсальный интерфейс. Ответственности разделяются:

- `AuthGateway` — OAuth и auth-сессия;
- `AccessRepository` — допуск и административные операции;
- `StudyRepository` — прогресс и попытки;
- `PairRepository` — пары, приглашения и оценки;
- `LiveSessionRepository` — состояние синхронной сессии;
- `AudioRepository` — локальные blobs и private Storage.

`DexieStudyRepository` остаётся локальным адаптером. Облачный слой записывает изменения локально сразу, затем отправляет их в Supabase через outbox. После восстановления сети очередь повторяется идемпотентно.

Правила конфликтов:

- попытки и оценки append-only и имеют глобальные UUID;
- прогресс темы объединяется по серверной ревизии и времени обновления;
- удаление и отзыв доступа всегда сильнее локальных изменений;
- состояние live-сессии изменяется атомарными RPC-командами;
- Realtime сообщает об изменении, а актуальное состояние повторно читается из БД.

## Первый вход и миграция

После успешного допуска пользователь выбирает один из вариантов:

1. Начать новый личный профиль.
2. Перенести данные из существующего IndexedDB.
3. Импортировать резервную копию JSON.

При обнаружении прежних двух локальных профилей мастер миграции просит выбрать, какой профиль принадлежит текущему GitHub-пользователю. Его личные записи загружаются в облако. Второй профиль не становится фиктивным облачным пользователем: для него создаётся приглашение реальному GitHub-аккаунту, а данные прикрепляются только после принятия приглашения.

До подтверждения миграции исходная IndexedDB не очищается. Экспорт JSON остаётся доступным как независимая резервная копия.

## Соло-подготовка

Экран «Устный ответ» становится самостоятельным сценарием:

1. Выбрать тему вручную или получить рекомендацию из слабых тем.
2. Запустить таймер подготовки.
3. Ответить без подсказки.
4. По желанию записать голос через `MediaRecorder`.
5. Прослушать запись.
6. Открыть короткий и расширенный ответы.
7. Заполнить устный чек-лист и самооценку.
8. Сохранить попытку и рекомендацию повторения.

Запись не обязательна. Отказ в разрешении микрофона не блокирует тренировку. Формат выбирается через `MediaRecorder.isTypeSupported`; сохраняются фактический MIME type и размер.

Локальную запись можно удалить, скачать или явно отправить партнёру. Она не загружается автоматически.

## Подготовка в паре

### Создание пары

Допущенный пользователь создаёт одноразовое приглашение и отправляет ссылку другому допущенному GitHub-пользователю. Приглашение действует 24 часа, хранится в виде хеша и погашается транзакционно.

### Синхронная сессия на двух устройствах

- один участник создаёт сессию;
- партнёр подключается со своего устройства;
- Presence показывает подключение обоих участников;
- БД хранит тему, отвечающего, проверяющего, этап и ревизию;
- отвечающий управляет подготовкой и завершением ответа;
- проверяющий получает чек-лист только после завершения ответа;
- сохранение оценки атомарно фиксирует попытку, оценку и смену ролей;
- повторное подключение восстанавливает сессию из БД.

Сессия подходит для людей в одном помещении или использующих внешний звонок. Передача живого аудио через WebRTC не входит в первую версию.

### Асинхронная проверка

Пользователь может явно загрузить записанный ответ партнёру. Партнёр получает задачу, слушает запись и заполняет тот же чек-лист. После оценки автор видит обратную связь.

Ограничения первой версии:

- не более 5 минут и 15 МБ на запись;
- private Storage bucket;
- автоматическое удаление через 14 дней;
- ручное удаление автором возможно раньше;
- метаданные попытки и оценка сохраняются после удаления аудио.

## Интерфейс

После входа главная страница показывает:

- «Готовиться одному»;
- «Готовиться с партнёром»;
- личный прогресс;
- готовность пары по более слабому участнику;
- ожидающие оценки;
- рекомендации повторения;
- статус синхронизации.

Администратор дополнительно видит раздел «Доступ», где может добавить login, назначить роль, отозвать доступ и посмотреть журнал изменений.

## Ошибки и восстановление

- Недопущенный пользователь получает отдельный экран без доступа к данным.
- Отозванный доступ немедленно блокирует прикладные запросы через RLS; интерфейс завершает локальную сессию при следующей проверке допуска.
- Потеря сети переводит запись прогресса в outbox и показывает статус без штрафа пользователю.
- Конфликт live-сессии возвращает актуальную ревизию и предлагает продолжить с неё.
- Ошибка микрофона оставляет доступным обычный устный режим.
- Ошибка загрузки аудио сохраняет локальную запись до повторной попытки или удаления.
- Удаление пары архивирует связь, но не удаляет личную историю участников.

## Проверки

- Unit-тесты допуска, конфликтов синхронизации, ротации ролей и срока хранения аудио.
- Интеграционные тесты SQL migrations, RPC и всех RLS-политик для anonymous, denied, member, partner и admin.
- Тесты миграции IndexedDB и JSON без появления третьего профиля.
- Компонентные тесты auth gate, соло-тренировки и ошибок микрофона.
- Playwright с двумя browser context для создания пары, подключения, оценки и смены ролей.
- E2E для отозванного whitelist-доступа и попытки чтения чужой пары.
- CI применяет миграции к локальному Supabase и запускает интеграционные тесты до деплоя.

## Этапы поставки

1. Supabase, GitHub OAuth, whitelist, admin UI, RLS и аудит доступа.
2. Облачный профиль, Dexie outbox, миграция существующих данных и личный прогресс между устройствами.
3. Новый соло-режим и локальная запись/прослушивание голоса.
4. Пары, приглашения и синхронная Realtime-сессия на двух устройствах.
5. Асинхронная отправка аудио, private Storage и автоматическое удаление.
6. Офлайн- и security-hardening, проверка восстановления и документация эксплуатации.

Каждый этап поставляется отдельными смысловыми коммитами и проходит `npm run verify`, профильные интеграционные тесты и Playwright перед push.

## Вне объёма

- встроенный аудио- или видеозвонок;
- распознавание речи;
- AI-оценка ответа;
- автоматическая публикация голосовой записи;
- публичные рейтинги;
- больше двух участников в паре;
- утверждение, что внутренний показатель готовности предсказывает результат экзамена.

## Критерии готовности

- Пользователь вне whitelist видит только экран отказа в доступе и не может получить прикладные данные через API.
- Администратор управляет whitelist по GitHub login, а доступ привязан к постоянному GitHub ID.
- Допущенный пользователь может готовиться один на любом своём устройстве.
- Два допущенных пользователя могут создать пару и провести синхронную сессию на разных устройствах.
- Соло-тренировка работает без микрофона; запись является необязательной.
- Аудио загружается только после явного действия и доступно только паре.
- Локальные данные текущей версии можно безопасно перенести в облако.
- Потеря сети не уничтожает завершённую попытку.
